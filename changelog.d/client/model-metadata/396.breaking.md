- **Views expand no relations by default (`storeModelConfig`)**:
    - The generated model config's `expand` is now empty for every view, where it named every declared expand. A list for a model with declared expands no longer fails with a 400 when its viewset sets no `permit_list_expands`. Read, create, and update requests send no `e` unless the config names an expand.
    - A form renders a foreign key with its mapped widget, such as a select, instead of an inline fieldset of the related serializer's fields. A list column for a foreign key labels each cell with the related object's primary key.
    - Building a model config now checks `expand` and dotted field list entries, and throws an error naming each problem, for every view. An `expand` entry must name an expand that model info declares. A `displayFields`, `fetchFields`, or `submitFields` entry such as `employee.username` needs `employee` in the same view's `expand`. A dotted entry must otherwise start with a model field, `related`, or `calculated`. Before, a list sent such a configuration to the server and got a 400. A create view never sent an undeclared expand, so nothing reported it.
      _Add each relation a view should expand to that view's `expand` with `setConfig`. A list also needs the relation in the viewset's `permit_list_expands`._
