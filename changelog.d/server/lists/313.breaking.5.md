- **A column total counts a matched row once, whatever the query joined to match it**:
    - `ListRowLevelViewSetMixin.get_column_info` now aggregates over the matched rows re-selected by primary key rather than over the filtered queryset directly. `SUM` counts a row once per joined match, so a `filterset_class` filter, a search, or a `RowLevelPermissions.check_queryset` `Q` that reached across a reverse foreign key or a many-to-many used to multiply every total in the response, silently, as a number that looked plausible. `vueda_info.E011` only constrains the path a total _declares_; this is the join arriving from how the request found its rows, which no check can see.
    - A list queryset that picks one row per group with `distinct(...)` (a `DISTINCT ON` without the primary key) gets totals over the rows it lists, because the re-selection keeps its ordering and distinct fields. A `DISTINCT ON` that names a queryset annotation cannot be carried that way, so a totals request over one raises `NotImplementedError` naming the viewset and the annotation.
      _No change for a request whose filters stay on the model's own columns or forward relations. A viewset overriding `get_column_info` aggregates however it always did, and should re-select by primary key if its filters can span a multi-valued relation._
