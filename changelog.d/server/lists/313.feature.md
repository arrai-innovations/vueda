- **`list` callers name the column totals they want**:
    - A new top-level `COLUMN_TOTALS_PARAM` setting (default `ct`) names the `list` query parameter that requests column totals, alongside `PAGE_QUERY_PARAM` and `PAGE_SIZE_QUERY_PARAM`. Repeating the parameter and comma-separating one value mean the same thing; a wildcard value (`*` or `~all`, matching `e` and `f`) requests every declared total; empty values and duplicates are dropped. A name the viewset does not declare is a `400` listing the valid totals, even alongside a wildcard. The parameter is accepted on `list` and rejected on `retrieve`, and it is separate from the sparse-fields parameter: `f` continues to select row fields only, and a total name is never a valid `f` value.
    - Model info gains a `model_column_totals` expandable section reporting `{"fields": [...]}`: the declared total names, in declaration order. A separate section rather than a flag on `model_fields`, because a total is named after a client column and need not match any serializer field. The section reports which totals exist, not the parameter that asks for them: a client sends that from a constant of its own, so a project that changes `COLUMN_TOTALS_PARAM` needs a matching client change, as it does for every other wire parameter. Reporting parameter names in metadata is planned for after v3.0.0, for the parameter set as a whole.
    - The generated OpenAPI schema documents the parameter on every `list` operation whose viewset declares totals, enumerating that endpoint's own total names alongside the wildcards. It is neither a pagination parameter nor a filter backend's, so drf-spectacular could not discover it on its own; `VuedaBaseAutoSchema.get_override_parameters` adds it.
    - A new `vueda_info.E011` system check validates every registered viewset's `column_totals`: the declaration must be a mapping; each key must be usable as a Django aggregate alias and must survive being read back out of the totals query parameter (so no comma, not empty, and not a wildcard spelling); each value must resolve to a real field on the model, must not reach through a relation that can match more than one row, and must land on a summable column (a numeric field or a `DurationField`).
    - The alias half of that is asked of Django rather than restated, so a key is held to the rule the installed Django enforces and a rule a later Django adds arrives with the upgrade. Nothing else about a key's spelling is constrained: `sales.total` and `2024_total` are as workable as `product_price`, because a key is a JSON object key on the way back rather than an identifier in either language.
    - A new `vueda_info.W002` warning reports a total whose name contains a percent sign. Django deprecated percent signs in column aliases in 6.0 and removes them in 7.0; VUEDA accepts such a name for as long as Django does, and warns at `manage.py check` time rather than leaving the failure for an upgrade. The warning tracks the installed Django rather than restating its rule, so on Django 5.2 (which has no such deprecation) the same name is accepted silently and reports nothing.
      _Run `manage.py check` in your build or deploy pipeline. Django does not run system checks when starting a WSGI application, so a deployment that never invokes the command still ships whatever it declared._
