- **A column total may name a queryset annotation**:
    - `vueda_info.E011` resolves the viewset's queryset and accepts a `column_totals` path naming one of its annotations, instead of requiring a field it can walk to through `_meta`. This is the allowance `vueda_info.E006` already makes for an annotation named in `ordering`/`ordering_fields`, so the two declarations now accept the same paths. A path that is neither a field nor an annotation is still an error, because catching a typo is most of what the check is for. When the queryset cannot be built without a request, the path rules are skipped rather than guessed at, the way the ordering check skips its own.
    - `get_column_info` sums an annotation in a separate `aggregate()` call from the totals over real columns, over a distinct `(primary key, value)` subquery, and reads its zero from the annotation's own `output_field` so a duration-valued annotation totals `timedelta(0)` rather than `0` over an empty set. The two cannot share a call: a column is summed over the matched rows re-selected by primary key, and an annotation cannot move onto that re-selection, because the expressions on a queryset are resolved against it and carry its table aliases. Both routes count a matched row once, so a filter or search joining a multi-valued relation multiplies neither kind.
      _Nothing to do. A total over an annotation now passes `manage.py check` instead of failing it. The declaration is still less protected than a real column, which is additionally checked for a summable type and a single-valued path. Prefer a `GeneratedField` or a database view where the value could be a column. An annotation that reads the multi-valued side of a join (`F("tags__weight")`) has a value per joined row rather than per row, and no total over it is meaningful._
