- **`makeworkflowmigrations` matches changes to the writes they describe**:
    - A state or transition code used by more than one row over time produced a migration holding an earlier round's writes while omitting its own. A code identified only the newest row that had ever carried it, so a change recorded before that row existed matched a later round's writes. A coded reference is now answered against each candidate write, using the ids that write recorded and the moment it was recorded, so it resolves to the row the code named at the time.
    - Writes belonging to a state or transition that the same round deleted never reached a generated migration. That row's permissions, and the source rows it parented, were dropped before matching began. They are now included, so a round that removes rows carries everything it removed.
    - Reversing a generated migration restored stale values for a row written three or more times. A change recorded what an update changed from by reading the row's earliest earlier write rather than the one immediately before it, so reversing returned the values the row was created with. Applying a migration was unaffected, which is why this was only visible on the way back.
    - A workflow code released by one model and taken over by another sent every change belonging to the first workflow to the second one's app. Those changes were skipped for the app they belonged to, their writes reappeared in a newly generated migration, and the second workflow's own writes were consumed in their place. A workflow reference in a newly generated migration now records `historical_app_label` and `historical_model` alongside `code`.
    - On a database that applied a generated migration rather than faking it, that migration's changes could claim a workflow edit made locally afterwards, and the edit was then missing from the next generated migration. Where it was the only local edit, the command reported `No workflow changes detected.` and wrote no migration at all. A migration that wrote its own changes on a database now leaves later edits alone. It still accounts for the edits it was generated from, so an author who fakes a migration, rolls it back and reapplies it does not see those edits again in the next generated migration.
    - A transition or other row added after its workflow's code was renamed reappeared in every newly generated migration. Its change names the rows it points at by the codes they held when it was written, but a nested reference, such as the workflow of a transition's target state, was read as it stood when that state was last written, which was before the rename. Every reference in a change is now read at the moment the write it describes was recorded.
      _No action is required beyond upgrading. These corrections are in the command rather than in the functions copied into generated migrations, so `updateworkflowmigrations` does not need to run. Migrations generated before this release keep matching on `code` alone, which stays correct unless a workflow code has moved between models. Review any migration generated before this release for a round that reused a state or transition code: its recorded changes were written by the old matching and upgrading does not correct them._
