- **`updateworkflowmigrations` names the workflow behind a reused code**:
    - Migrations generated before this release refer to a workflow by its code alone, which cannot say which workflow a change meant once another model has taken that code over. The command now adds `historical_app_label` and `historical_model` alongside the code in every workflow reference in `changed_data`, working out what each code meant when each change was recorded from the workflow's own change. It adds to the values the change data records and never removes or alters one, leaves a workflow whose own change it cannot find as it is, and makes no further difference when run again. A `changed_data` list that gains anything is written back whole in the form `makeworkflowmigrations` writes it, so a comment or formatting inside that list is not kept; a list with nothing to add is left exactly as it was, and hand-added imports and functions elsewhere in the file are always kept. A migration whose `changed_data` cannot be read, because the file has a syntax error, has been altered so that it no longer runs on its own, or holds a change without the `model_name`, `history_date`, or `changes` the command reads, is skipped in full and reported by path, the other migrations are still updated, and the command finishes with a failure rather than rewriting a file it cannot read. A `history_date` recorded without a time zone, which only a hand edit produces, is reported and read as UTC so that it still orders against the dates other migrations recorded, and is left in the file as it was written.
      _Run `python manage.py updateworkflowmigrations <app_label> ...`, naming only your own apps, and commit the rewritten migrations. Always name the apps: with none, the command also rewrites VUEDA's own migrations inside the installed package, such as `vueda_vdq`'s, which you cannot commit and which then fail to apply. After the run, restore from version control any rewritten migration whose `vueda_workflow` dependency is earlier than `0008_initialstateevent_objectstateevent_stateevent_and_more`, which is any migration generated with v3.0.0a0 or earlier. The rewrite gives it functions that need models that migration adds, so it no longer applies and fails with `LookupError: App 'vueda_workflow' doesn't have a 'ObjectStateEvent' model`; [#298](https://github.com/arrai-innovations/vueda/issues/298) tracks this. A restored migration keeps naming its workflow by code alone. The rewritten files are not formatted to any project's style, so run your formatter and linter on them before committing. Run the command as a development step, not during a deploy: the files it rewrites are not the ones the next deploy starts from. Migrations generated before this release keep working until a workflow code is taken over by a different model, and updating one that has already been applied elsewhere is safe, because the change data describes the same workflow records either way._
